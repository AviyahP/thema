## What `name-v4` changes, and why

### 1. Task B stops showing three arbitrary members

`name-v3` gave an internal node its children's names, its direct members as bare
`[source] name (inclusion)`, and three "representative members". Those three were
`member_keys[:3]` -- the first three rows of `members.tsv` for that node, which is grouping order.
Not medoids, not highest-inclusion, not sampled. "Representative" was not true of them.

The test that matters is whether a sample was even a DIRECT member, because a sample sitting inside
a child tells the model nothing the child's name did not already say. Measured over the 20 nodes in
`task_b_render_20.md`: **10 of 60 samples were direct members.** The other 50 described biology the
model could already see.

`name-v4` drops them and gives every direct member its source, name, inclusion and full
description, highest inclusion first. The effect on prompt size is not uniform and that is the
point -- nodes with no direct members get **51% shorter**, nodes with three or more get slightly
longer. Median over the 20: 697 words to 737.

The coverage rule is unchanged in substance and now stated in Task B's own words: the name must be
true of every child's name and every direct member at inclusion 0.5 or above, may leave out direct
members below 0.5 if it names them in the rationale, and a member below 0.5 is never on its own a
reason to refuse.

### 2. The full Task C pass is withdrawn

`name-v3` sent every theme with a parent or a sibling to the model -- **806 of the run's 1,676
calls, 48%** -- to be asked a question string comparison answers. It cost roughly half the run and
made the result worse three ways:

- **It created 20 duplicate names.** 10 names on 20 themes, and **all 20 arrived at the duplicate
  via a revision** -- not one survived from generation. Two themes told independently and
  concurrently that their name collides can both revise onto the same replacement, and no revision
  was re-checked.
- **It narrowed parents below their own children**, in 2 of the 3 wrong parents found in the
  20-node read. A parent that no longer covers its own children states something false about the
  hierarchy, which is worse than a name that merely reads awkwardly.
- **It produced one false refusal.** `n0475` was declared unnameable because "both children are
  identically named Gametogenesis and reproductive development" -- a refusal caused by the pass's
  own duplicate.

Under `name-v4` detection is mechanical: global uniqueness across the whole DAG and repeats-parent,
both by string comparison, and only the names that actually collide are re-asked. A replacement for
a node with children is accepted only if it still covers every child, checked by
`covers_children()`; a replacement that fails is **discarded and the colliding original kept**, and
the discard is reported. "More specific, never broader" now applies to leaves only, because for an
internal node it was the instruction that caused the narrowing.

`covers_children()` is deliberately weak -- it asks only that every child still shares a content
word -- and is used to REJECT, never to accept. A revision that passes it is not thereby correct.

### 3. Leaf names carry over; the version is `name-v4`

`NAME_PROMPT_VERSION` is `name-v4`. A new constant `LEAF_PROMPT_VERSION` stays at `name-v3`,
because **every change above is confined to Task B's user message and to Task C**, and a leaf's
request is `Request(theme_key(member_keys), SYSTEM_PROMPT, render_leaf(...))` -- all three parts
untouched. The Task B wording lives in `render_internal`, not in the shared system prompt, which is
what makes this possible.

Verified rather than asserted: HEAD's `naming.py` was loaded in its own package tree beside the
working tree's, and both `sha256(SYSTEM_PROMPT)` and `sha256(render_leaf(...))` came out equal --
`a7d93ced5b37f37c` and `ada95d6410d54265`. Those two digests are now pinned in
`tests/test_naming.py`, so if either artefact changes without `LEAF_PROMPT_VERSION` being bumped the
test fails loudly instead of the cache answering quietly.

A ledger is opened per `(model, version)`, so pointing leaves at `name-v3` reuses all **285 leaf
completions for $0.00** while every internal node and every collision call is a miss. Routing is
per request rather than per level, so it stays correct if the level structure changes.
