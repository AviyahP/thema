### What already exists and transfers unchanged

- **The scramble function takes any matrix.** `recurrent.null_embeddings(x, seed)` is signature
  `(n, dim) -> (n, dim)`: it permutes each column independently and renormalises rows, with no
  dependence on the universe, the source mix or the dimension. So **Reactome-only, GO-only, synthetic
  and SPECTER2 universes all scramble with the existing code**, which is what test F step 5 needs.
- **Floors transfer is already gated.** `--floors-from` refuses unless `n`, `runs`, `scramble_rows`,
  `size_cap`, `inclusion_cut`, `universe_digest` and `space` all match — so applying the 10,770
  floors to a new universe will be **refused by design** and needs the same `--half-build-floors`
  style escape hatch, or a declared widening of the guard. **Flagged as a change the protocol
  implies but does not mention.**
- **G4/STRING is built and run-ready** (`scripts/string_coherence.py`), with STRING v12 already
  downloaded (83 MB links, 13.7 M edges; 20 MB aliases).
- **The paired cluster bootstrap exists** (`engine_scores.py`), but its cluster labels are
  `_parent_of(...)`, the **smallest shared curated parent**. The protocol specifies the **top-level
  Reactome pathway** and **the child of biological_process** instead, with lexicographic
  tie-breaking. Different definition, so it needs new code.

### Ambiguities in the protocol — questions, not resolved here

As instructed, these are written down and **not** answered.

1. **Test F step 5 vs the floors guard.** The guard refuses `--floors-from` when `n` or
   `universe_digest` differs, which is every new universe. Should it be widened for this protocol,
   or is "apply the 10,770 floors to a new universe" meant to go through a declared override like
   `--half-build-floors`?
2. **E1 (ii) "full-build restricted" and `min_size`.** A theme cut to its Reactome members can fall
   below 3 and is dropped — but should the *bands* then be assigned by the restricted size or the
   original theme size? The two give different band populations.
3. **E2 band definition.** Bands are "set by curated (or planted) term size", and a planted node's
   size is its descendant count. Is a planted node with fewer than 3 descendants excluded as in E1?
4. **σ\* is fixed by "mean top-15 cosine" of the real Reactome-only centred vectors** — but the
   Reactome-only universe does not exist yet, so σ\* cannot be computed until it is built. Is σ\*
   therefore fixed *after* the Reactome-only build and *before* any synthetic engine run, which is
   how I read it?
5. **§H selection says "mean recall over the 4 bands × 2 sources on the E1 tuning half"**, but E2's
   tuning is "replicate 0 at σ\*", which has one source. Is E2's HiDeF-tuned selected on mean recall
   over the 4 planted bands only?
6. **"Fewer knobs" as a tie-break** (final rule clause 2). A has the cap, inclusion cutoff, θ, tol,
   stray and Jaccard; B adds a 10-rung ladder and k. Is the count meant to be of *free* parameters,
   and does the ladder count as one knob or ten?
7. **Clause 1 requires a win in "at least one fine-band cell"**, and arm B has no floor reaching
   FDR ≤ 0.01 in the 3- and 4-member strata — so it cannot build a 3–10 theme at all. Is the 11–50
   band sufficient to satisfy "fine", or must the 3–10 band be winnable for B to qualify?
8. **Does test F's decision apply per arm or globally?** "Every later build in this protocol uses the
   form decided here" — if A drops floors and B keeps them, do A and B then differ in a way the
   comparison has to account for?

# §1.1 The adapter, and how little had to change

**The pipeline was already engine-agnostic and I did not expect that.** Three fields of a `Run` look
tree-shaped, and only one is used by matching:

| field | what it is | used by matching? |
|---|---|---|
| `chain_indptr` / `chain_idx` | **an inverted index**: pathway → the candidates containing it | **yes** |
| `parent` | smallest candidate strictly containing each candidate | **no** — written, never read |
| `leaf_cluster` | smallest candidate containing each pathway | **no** — written, never read |

And the selection rule `_score_matrix` applies is already *"the run's candidate with the greatest
overlap with the grouping's shared members, ties toward the smaller"* — written for the two-sided
change on 2 Oct. **That is exactly the rule a flat partition needs.** So §1.1's requirement needed
one new constructor, `run_from_candidates`, that builds the inverted index directly instead of by
climbing `parent`, and **no change at all to matching, completion, consensus or the gate.**

`cut_trees.load_run` now goes through that same constructor, so the Ward path and every new engine
build their candidates with one piece of code. That is what makes §1.2 a real test rather than a
formality — if Ward kept a private path, byte-identity would prove nothing.

**Five tests**, including the strong one: fed Ward's own candidates and nested structure on four
seeds, `run_from_candidates` reproduces `_one_run`'s `Run` **field for field**.

### The matching rule, confirmed in code rather than asserted

Amendment 4 restates that containment in a larger community does not count as recurrence, so I
checked the code implements it. A 10-member grouping whose only appearance in four other runs is
inside a 50-member community gets support **1/5** — its own run and nothing else — because the
two-sided Jaccard is 10/50 = 0.2. A genuine near-copy, 9 of 10 members shared plus one extra at
Jaccard 0.818, gets **1.0**. Without the two-sided rule, a run proposing one huge community would
"find" every grouping it contained and a coarse engine would score as perfectly recurrent. That is
the failure mode the amendment guards, and it was already guarded. Two tests now pin it.

### Three ladder changes, and what protects them

Declared [0.001, 100] → top widened to 300 → bottom raised to 0.0669433. **Every change was made
before any arm had a score, each was driven by a measurement of the setup rather than of an outcome,
and each is recorded with the number that forced it.** The honest risk in a sequence like this is
that a setup drifts toward whatever will eventually look good. The protection is that none of the
three could have been informed by a result, because no result existed — and the one-shot stop rule
leaves no second round in which to use one.

mismatch. It is recorded in each half's manifest.

arm**, which is what a comparison needs. Arm A's properly calibrated 100-run halves already exist,

two arms is a difference on identical data. One consequence is that every pairwise CI
the dominance rule needs comes from subtracting two stored curves, so adding an arm

Nine tests on the rule itself, on hand-built curves where the answer is known:
dominance needs BOTH a significant win and no significant loss; a win inside the 0.02
margin dominates nothing; max-min scores an arm by its worst cell against the best

cannot win even when it is best everywhere. One test records a fragility rather than
smoothing it: 0.52 - 0.50 is 0.020000000000000018 in binary floating point, so a pair
a reader would call exactly 0.02 apart can dominate. No tolerance was added, because
choosing one is a tuning decision and §0 forbids tuning -- but a verdict resting on a
gap within a hair of 0.02 should be read as a boundary case and said to be one.

G4 is STRING v12 at combined score >= 700, and it earns its place because every other
gate and score is computed from the same embeddings the engines cluster: an engine
that exploited a quirk of the embedding could pass all of them. STRING is independent
evidence. The null draws from STRING-COVERED genes only -- drawing from all pathway
genes would compare a theme against sets containing genes STRING has never seen,
which have no edges by construction, and every theme would look enriched. Densities
