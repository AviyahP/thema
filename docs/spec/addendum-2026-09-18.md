## A. Conflicts

### A1 — Demo data loading: a global, not `fetch`
**Supersedes §20.1.** Generate `demo/ontology.js` assigning a global, exactly as `prototype.html`
already does. No `fetch`. Reason: `fetch` is blocked on `file://` in every mainstream browser and
the page must open by double-clicking it.

### A2 — Versioned ontology directories are committed
**Supersedes the current `.gitignore`.** Everything under `data/ontology/v0.1/ward_tree/` is
committed; add `!data/ontology/v*/` to `.gitignore`. Size is revisited when the 10,817 build exists,
not before.

### A3 — No synthetic root, anywhere
**Supersedes §9.4 and the mock `DATA`.** `ward_tree`'s roots are the k10 nodes — a forest, exactly
like `recurrent_dag`. Remove `"All themes"` from the mock `DATA`. The detail card's empty state
still shows the ontology summary; **that is a view, not a node**, and must not appear in the tree or
in `ontology.json`.

### A4 — Versioned build artefacts are replace-within-version
**Clarifies the no-overwrite convention; also to be recorded in `DECISIONS.md`.** A version
directory is built to a temp dir, validated, then swapped atomically. Merge-never-replace applies to
**shared tables** — descriptions, experiments — where two runs contribute different rows that must
coexist. It does not apply to **versioned build artefacts**, where a rebuild legitimately supersedes
its predecessor in full. `merge_tsv` on `nodes.tsv` keyed by a per-build generated id would
accumulate stale nodes; that is the failure this distinction prevents.

### A5 — The manifest records which descriptions it was built from
**Extends §8.** `manifest` carries `prompt_version` and the sha256 of the descriptions table. The
ontology is a pure function of those descriptions, and as of 2026-09-18 the table keeps every
generation; without this, two ontologies built from v3 and v4 text are indistinguishable.

### A6 — The build line renders from the manifest
**Extends §8, confirms §19.1.** The manifest records the source versions read from
`data/raw/VERSIONS.txt`. The masthead build line renders from the manifest, never typed.

### A7 — Sequencing and the 10,817 price
**Supersedes §21.5.** The ~$176–232 figure included verification and repair (arm B), which is
**parked**. Arm A alone — the v4 prompt, no verify, no repair — is to be priced for the 10,817 and
checked against the ~$81 estimate.

Order is fixed: **complete the 1,854 first** (the ~1,650 not yet cached), demo on it, *then* decide
on the 10,817 — and separately on whether verification runs at scale at all. Nothing is submitted
until Aviyah says so, per command.

## B. Underspecified

### B1 — If `3 × null_max >= 0.5`, fail the build
**Supersedes §10.6.** Do not clamp. Report `null_max`. That outcome means resampling produces
recurrent structure by chance and the method is not discriminating on this data — **a finding, not
a knob.**

### B2 — PARENT-BEYOND, definitively
**Replaces the ambiguous sentence in §3.2.** Per `DECISIONS.md` entry #1, unique-removal:

> **L(P) = genes(P) minus { g : g is in some significant child of P, and in no non-significant
> child of P }**

- Genes shared between a significant and a non-significant child **stay in L**.
- Genes of P in no child at all **stay in L**.
- **Full-removal** — drop every gene in any significant child — is the exposed alternative
  parameter, **off by default**.

### B3 — Numeric go/no-go for §14
**Supersedes §14's prose thresholds.**

| item | Go condition |
|---|---|
| §14.2 gene-overlap validation | median Jaccard of contested members **≥ 2 ×** the random-non-member median **AND** Mann–Whitney **p < 0.01** |
| §14.3 no regression | ancestor-pair F1 **within 0.02** of `ward_tree` **AND** reactome2go recovery **within 2 percentage points** |

### B4 — v0.2 scope is the 1,854 only
**Supersedes §10.10's scaling note.** `numba` is deferred; the decision is taken after §14 results,
not before.

### B5 — Partial coverage never refuses
**Supersedes §2's coverage condition.** Compute BASIS only for nodes whose members are **all**
present in the table. Render the rest as `not computed — N of M members untested`. Show overall
coverage % at the top of the results. `thema.gmt` ships with v0.1.

### B6 — The reproduce panel diagnoses honestly
**Supersedes §3.5.** The panel shows THEMA's set size beside the user's for each pathway. It
diagnoses **"universe"** only when the set sizes match; otherwise it says **"set composition differs
(source version / HGNC resolution)"**. Reason: THEMA's sets differ from the user's by source version
and by HGNC resolution — `DECISIONS.md` already records members discarded as unresolvable — so
"almost always the universe" was wrong.

### B7 — Rung 3 is a hard requirement for the worked examples
**Supersedes §5.** A declared or assumed universe is **not acceptable**. Datasets must have
deposited processed count matrices, so the measured universe is the set of genes detected in the
matrix — **derived from the data, not assumed**. Claude Code proposes three candidates with GEO
accessions and the derivation for each universe; **Aviyah chooses**.

### B8 — Theme-chip rule, method-independent
**Supersedes §12's chip note and §19.3.** The chip shows **the smallest node containing all the
listed pathways**: its size, and on the landing page the method name. Under `ward_tree` this
reproduces 15 (NF-κB, k200) and 18 (insulin, k50). Under `recurrent_dag` it is whatever the DAG
gives, or **"no single node contains all four"** if none does — which is itself worth showing.
